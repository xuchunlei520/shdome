# SHDome 极简应用市场设计

## 1. 目标

SHDome 应用市场面向不熟悉 Docker 的服务器用户。官方应用应做到“选择应用后一次确认完成安装”；自定义单容器应用应做到“提供镜像后一次确认完成安装”。Manifest、Compose、端口冲突处理和运行环境初始化由平台负责，不进入普通用户的必填流程。

本设计在保留现有安全边界、生命周期、域名、备份和更新回滚能力的前提下，增加以下功能：

1. 官方应用自动选择可用端口，安装前只确认一次。
2. 用户可以通过 Docker 镜像创建、安装、导入、导出和删除自定义应用。
3. 官方应用与自定义应用统一展示，同时明确来源。
4. 官方目录可以独立刷新、校验和回滚；未配置远程目录时继续使用发布包内置目录。
5. SHDome 自身升级不得覆盖用户自定义应用。

## 2. 本期范围

### 2.1 包含

- Schema 1 单容器应用。
- 固定 tag 的 Docker 镜像，不接受 `latest`。
- 从镜像元数据读取公开端口和声明卷。
- 未提供主机端口时自动选择可用端口。
- 自定义应用的创建、导入、校验、查看、导出和删除。
- 官方目录签名校验、暂存、原子切换和上一版本回滚。
- 进入交互式应用市场时，按检查间隔静默尝试刷新已配置的官方目录。

### 2.2 不包含

- 任意 Docker Compose 导入。
- 多容器、数据库和 Redis 编排。
- `privileged`、Docker Socket、宿主机网络、设备映射。
- 安装前后 Shell 钩子。
- 第三方社区源。

这些能力需要 Schema 2 和独立的风险模型，不能通过放宽 Schema 1 绕过。

## 3. 用户流程

### 3.1 官方应用

```text
应用市场 → 选择应用 → 立即安装 → 完成
```

安装页显示推荐结果，但不要求用户逐项输入：

```text
应用：Uptime Kuma
访问端口：3001（端口冲突时自动选择其他端口）
数据目录：/opt/shdome/apps/uptime-kuma

确认开始安装吗？ [y/N]
```

需要指定端口的用户使用高级参数 `k app install <id> --port <port>`。

### 3.2 自定义应用

```text
添加自定义应用 → 输入固定版本镜像 → 确认创建并安装 → 完成
```

系统自动生成应用 ID、名称、容器名、架构、端口、卷和健康检查。镜像没有声明端口时，只追问容器端口；非交互调用必须提供 `--container-port`。

对应 CLI：

```text
k app custom add <image> [--name <name>] [--container-port <port>] [--host-port <port>] [--no-install] [--yes]
k app custom import <manifest.json> [--replace]
k app custom validate <id|manifest.json>
k app custom list
k app custom export <id> [output.json]
k app custom delete <id>
```

删除自定义定义前必须先卸载对应应用。删除定义默认需要一次确认。

再次添加同一自定义镜像的新固定 tag 时，SHDome 将其识别为更新：一次确认后替换目录定义，并复用现有备份、健康检查和失败回滚流程更新已安装应用。手工修改的 Manifest 使用 `custom import --replace` 更新定义。

## 4. 目录与优先级

```text
/opt/shdome/catalog/
├── official/
│   ├── current -> releases/<version>
│   ├── previous -> releases/<version>
│   └── releases/
├── custom/
└── refresh.json
```

- 发布包中的 `catalog/*.json` 是内置官方目录和离线兜底。
- 如果存在已验证的 `official/current`，使用它替代内置官方目录。
- `custom/` 永久位于数据目录，不随 SHDome 自身升级替换。
- 官方 ID 与自定义 ID 不允许重复；官方目录内部和自定义目录内部也不允许重复。
- 市场排序稳定：先按来源，再按应用 ID。

## 5. Manifest 来源

列表增加“来源”字段：

- `官方`：发布包内置或通过签名刷新的目录。
- `我的`：本机用户创建或导入。

安装后的应用保存 Manifest 副本，因此目录刷新失败不影响已安装应用的启停、备份或卸载。

## 6. 自动端口策略

1. 从 Manifest 读取建议宿主机端口。
2. 同时检查 SHDome 状态登记和系统监听端口。
3. 被占用时，从建议端口开始向上查找，直到找到可用端口。
4. 多端口应用分别查找，且本次安装计划内不能重复。
5. 显式传入 `--port` 时严格使用用户值；冲突直接报错，不擅自更改。

## 7. 自定义镜像推导规则

- 镜像必须包含固定 tag，拒绝 `latest`。
- 应用 ID 取镜像仓库最后一段，转为小写短横线格式；冲突时要求用户指定名称或 ID。
- 版本取镜像 tag。
- 架构取当前主机标准化架构。
- 端口取镜像 `Config.ExposedPorts` 中排序后的 TCP 端口；第一个 TCP 端口为主端口。
- 如果只有 UDP 端口，要求用户显式指定主 TCP 端口。
- 卷取镜像 `Config.Volumes`，映射到应用私有数据目录中的安全名称。
- 默认健康检查为 TCP；用户可以在导出的 Manifest 中使用受支持的 HTTP 或容器检查后重新导入。
- 镜像元数据只用于生成受限 Manifest，不能注入 Compose 字段或 Shell。

## 8. 官方目录刷新

目录制品为压缩包，配套 detached signature：

```text
catalog-<version>.tar.gz
catalog-<version>.tar.gz.sig
```

刷新命令：

```text
k app catalog status
k app catalog refresh --url <archive-url> --signature-url <sig-url> --public-key <pem-file>
k app catalog rollback
```

也可以通过管理员配置的环境变量提供默认 URL 和公钥。刷新流程：

```text
下载到临时目录
→ 使用固定公钥验证签名
→ 限制压缩包路径和文件类型
→ 校验全部 Manifest 及文件名
→ 检查 ID 重复
→ 写入版本目录
→ 原子切换 current
→ 保留 previous
```

刷新失败时不修改当前目录。未配置远程地址时，自动刷新静默跳过，市场继续使用内置目录。

## 9. 安全约束

- 自定义目录只接受通过 Schema 1 校验的 JSON。
- 自定义应用只能挂载 `/opt/shdome/apps/<id>/data/` 下的平台托管路径。
- 不执行 Manifest 或镜像标签中的命令。
- 导入文件大小设上限，拒绝符号链接和非普通文件。
- 官方目录必须验签，不能使用“与制品同源的 SHA-256 文件”代替身份验证。
- 下载、解压和验证在临时目录完成，最终目录使用原子切换。
- 自定义应用文件权限为 `0640`，目录权限为 `0750`。

## 10. 验收标准

1. 官方应用交互安装不再询问端口，只显示一次安装确认。
2. 推荐端口被占用时，未显式指定端口的安装自动选择下一可用端口。
3. `k app list` 同时显示官方和自定义应用及其来源。
4. `k app custom add <固定版本镜像>` 能生成合法 Manifest，并可选择立即安装。
5. 无公开端口的镜像在非交互模式缺少 `--container-port` 时明确失败。
6. `latest`、非法 ID、官方 ID 冲突和危险 Manifest 均被拒绝。
7. 已安装的自定义应用不能删除定义；卸载后可以删除。
8. SHDome 发布包更新不会覆盖 `/opt/shdome/catalog/custom/`。
9. 官方目录验签或 Manifest 校验失败时，当前目录保持不变。
10. 官方目录成功刷新后可以回滚到 previous。
11. 现有五个官方应用及原 CLI 生命周期保持兼容。
12. 官方目录在现有五个应用基础上首批增加 AList、FreshRSS、Syncthing 和 Vaultwarden。

## 11. 官方目录发布

维护者使用离线保存的 Ed25519 私钥构建目录制品：

```bash
bash scripts/build-catalog.sh <目录版本> <private-key.pem>
```

命令会在 `dist/catalog/` 生成压缩包、detached signature 和便于发布核对的 SHA-256。私钥不能提交到仓库或复制到目标服务器；目标服务器只保存公钥。
